# Raw-to-Silver Data Quality Reporting

## Overview

The Financial Market Data Platform produces a structured quality report for each successfully completed Raw-to-Silver processing operation.

The report summarizes accepted and rejected observations, rejection reasons, and quarantine file references.

## Report schema

| Field | Type | Description |
|---|---|---|
| `total_records` | Integer | Number of parsed observations |
| `valid_count` | Integer | Observations accepted by validation |
| `invalid_count` | Integer | Observations rejected by validation |
| `acceptance_rate` | Float | Accepted fraction between 0 and 1 |
| `rejection_rate` | Float | Rejected fraction between 0 and 1 |
| `violation_counts` | Object | Counts grouped by stable validation code |
| `quarantine_paths` | List of strings | Paths of quarantined observations |

Example:

```json
{
  "total_records": 2,
  "valid_count": 1,
  "invalid_count": 1,
  "acceptance_rate": 0.5,
  "rejection_rate": 0.5,
  "violation_counts": {
    "NEGATIVE_VOLUME": 1,
    "NON_FINITE_CLOSE": 1
  },
  "quarantine_paths": [
    "quarantine/example.json"
  ]
}
```

The example is illustrative; actual quarantine paths are generated by the storage layer.

## Counting rules

Each observation is counted exactly once as either valid or invalid.

The following invariant must hold:

`total_records = valid_count + invalid_count`

Acceptance and rejection rates are calculated using the total number of parsed observations and rounded to four decimal places.

When no observations are present in an independently constructed validation batch, both rates are defined as zero.

A rejected observation may contain multiple violations. Every violation contributes to its corresponding code count. Therefore, the total number of violation occurrences can exceed `invalid_count`.

Violation codes are sorted alphabetically to make reports deterministic.

## Integration

`build_quality_report()` aggregates the results of existing financial validation.

`process_raw_market_data()` generates the report after successful Silver and quarantine writes.

`process_raw_file_to_silver()` includes the report under the `quality_report` key.

Existing top-level fields remain unchanged, preserving compatibility with Airflow execution tracking.

## Error handling

A provider parsing failure prevents successful Raw-to-Silver processing and does not produce a successful quality report.

For parseable observations that violate financial rules, valid records can still reach Silver while invalid records are written to quarantine.

A reporting or storage exception fails the processing operation rather than returning a misleading success result.

## Path compatibility

The quality report serializes quarantine paths using forward slashes.

Existing top-level orchestration paths retain their original operating-system representation for backward compatibility.

## Security and limitations

Reports do not include API credentials or complete provider responses.

Quarantine paths may reveal local storage locations, so reports should be shared according to the project's operational access policies.

The report currently describes one Raw-processing operation; it is not a historical aggregate or a dashboard.

These tests use deterministic local fixtures and do not require live Twelve Data API access.
